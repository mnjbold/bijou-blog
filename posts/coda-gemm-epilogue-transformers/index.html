MOSS: Self-Evolution through Source-Level Rewriting in Autonomous Agent Systems

Transformer training is dominated by GEMMs (general matrix multiplications), but that doesn't mean GEMMs are the bottleneck. If you've ever profiled a training run, you've seen the familiar pattern: the dense linear algebra operations saturate your GPU's compute units, yet a surprising fraction of wall-clock time slips away into a long tail of tiny, memory-bound kernels — layer norms, activation functions, residual additions, scaling, and reductions. These operators do almost no arithmetic relative to the data they move, and every one of them means a round trip through global memory, stalling the pipeline.

A new paper from researchers at Stanford and NVIDIA — including Tri Dao of Flash Attention fame — proposes a clean solution that feels obvious in retrospect: fuse nearly all of these operations directly into the GEMM kernel as epilogue programs.

The Anatomy of the Problem

Consider what happens in a single forward pass of a Transformer block. After the attention sub-layer, you typically have:

1. A residual add (element-wise)

2. Layer normalization (read the entire tensor, compute statistics, scale)

3. The MLP projection (a GEMM)

4. A nonlinear activation like GELU or SwiGLU (element-wise)

5. The MLP down-projection (another GEMM)

6. Another residual add

7. Another layer norm

In most training frameworks (PyTorch, JAX, TensorFlow), each of these is a separate kernel launch. The GEMMs at steps 3 and 5 are compute-bound and efficient. But steps 1, 2, 4, 6, and 7 read the entire output of the previous operation from HBM, perform a trivial amount of work per element, and write the result back. After the GEMM produces its output tile and writes it to memory, the next kernel reads that same tile back, does a tiny computation, and writes it again. On modern GPUs, the ratio of arithmetic to data movement for these operations can be as low as 1–2 FLOPs per byte — far below the roofline's compute-bound threshold.

The paper reports that across representative Transformer workloads, these auxiliary operators can account for 20–40% of total step time in an otherwise optimized training stack, with the fraction growing as GEMMs themselves get faster through hardware improvements and better libraries.

CODA's Core Insight

CODA (CUDA Operator as GEMM Epilogue Abstraction) is based on a simple observation: the output of a GEMM is already on-chip in the GPU's shared memory and registers while the kernel runs. By the time the GEMM mainloop has accumulated its result for a given output tile, that tile sits in registers before being written back to HBM. If we can algebraically reparameterize the subsequent operations to execute right there — while the tile is still hot — we eliminate the read-back entirely.

The abstraction works like this:


GEMM mainloop → [optional: scaling] → [reduction/statistics] → 
  [pairwise transforms] → [accumulation] → write to HBM

Each of these epilogue stages is a composable primitive. The key constraint is that the "mainloop" — the tightly tuned, expert-written inner tile loop — remains untouched. CODA only intervenes in the epilogue, after the tile accumulator holds the GEMM result.

The composable epilogue primitives are:

  • Scaling: element-wise multiplication by a scalar or broadcast vector (used for residual scaling, dropout scaling)
  • Reduction: computing row-wise or column-wise statistics (used for mean/variance in layer norm)
  • Pairwise transformations: element-wise operations with fuseable constants (used for GELU, SwiGLU, ReLU)
  • Accumulation: adding results from multiple epilogue stages into a single output buffer

What Makes This Hard

You might wonder: why hasn't this been done before? CUTLASS and cuBLAS already support limited epilogue fusion — you can add a bias, apply a ReLU, or do an element-wise scaling after a GEMM. But CODA goes much further.

The difficulty is that operations like layer normalization require cross-tile statistical dependencies. Layer norm computes the mean and variance across the hidden dimension, then normalizes and scales. If your GEMM output tiles are partitioned along the hidden dimension (as they typically are for large hidden sizes), no single tile has enough information to compute the normalization. CODA solves this by introducing a two-pass epilogue: a horizontal reduction pass that aggregates statistics across tiles using shared memory, followed by the actual normalization pass that uses those statistics while the data is still on-chip.

Similarly, SwiGLU activation (used in Llama, Mistral, and most modern architectures) requires multiplying two slices of the GEMM output together. CODA handles this by arranging the GEMM to produce both halves of the SwiGLU input in the same tile, then applying the activation as a pairwise epilogue transform before the result is written.

Results That Matter

The paper evaluates CODA on a range of Transformer configurations at different scales. The headline numbers:

  • End-to-end training speedup: 1.15–1.32× across representative Transformer workloads (GPT-2, Llama-style, BERT)
  • Peak memory reduction: up to 1.4×, since intermediate tensors for layer norm and activation outputs never materialize in HBM
  • Kernel count reduction: a single CODA kernel replaces 5–7 separate framework kernels per Transformer block

But perhaps the most interesting result is this: LLM-authored CODA kernels achieve comparable performance to human-written ones. The paper shows that GPT-4o and Claude could produce correct and efficient CODA programs for the standard Transformer block when given the abstraction specification and a few examples. This suggests that constrained DSL-style abstractions (as opposed to open-ended CUDA programming) are a sweet spot for LLM-based kernel generation — the interface is narrow enough to be learnable, but expressive enough to cover the domain.

The Bigger Picture

CODA fits into a broader trend that is reshaping the AI infrastructure landscape.

First, the era of "just make the GEMMs faster" is ending. cuBLAS, CUTLASS, and Triton have pushed dense matrix multiplication close to hardware limits. The remaining headroom lies in the data taxi — the cost of reading and writing tensors between operations. Fusing operations into the GEMM epilogue is one of the last big levers for training efficiency.

Second, CODA represents a bet on abstraction over automation. Instead of trying to build an auto-fuser that discovers fusion patterns through search (the approach taken by XLA and TVM), CODA provides a principled algebraic framework where the fusion falls out naturally from the way you express the computation. This is the same philosophy behind Flash Attention: constrain the interface just enough to enable the optimization, then prove that the constrained interface is expressive enough.

Third, the LLM-generated kernel result is quietly significant. We've seen LLMs produce working CUDA before, but typically for small, well-scoped problems. CODA shows that with the right abstraction layer, LLMs can produce production-quality fused kernels for the full forward and backward pass of a Transformer block. This has implications for how we think about GPU programming in an AI-native world.

What To Watch

1. Adoption in training frameworks: The CODA abstraction is open-source and designed to be integrated into existing training stacks. Watch for major frameworks (PyTorch, JAX) to adopt CODA-style epilogue fusion in their compiler pipelines over the next few months. The authors have released code, and given Tri Dao's track record with Flash Attention adoption, this could move fast.

2. Extension to attention itself: CODA currently handles everything except attention in a Transformer block. An obvious next step is fusing the attention computation (or its linear-attention variants like Mamba, Gated DeltaNet-2, or KDA) into the same epilogue framework. A fully fused Transformer block — one kernel, no intermediate materialization — is the endgame here.

3. LLM-driven kernel optimization: If CODA's abstraction is learnable enough for today's LLMs to write production kernels, what happens when the next generation of models targets this DSL directly? We may see a shift in how GPU kernel libraries are developed: less human hand-tuning, more specification-in, kernel-out.
